# 《渔力全开》策划案内部矛盾与待决题

来源：`design`（策划案正文、钓鱼表、物品表、抽奖表）与 `docs/GameSpec.md` 的逐节对照核对。
去向：每题确认后从本清单删掉，移进[策划案已确认结论](策划案已确认结论.md)；本文件只留还没定的题。题号随删题重排，跨文件引用一律用问题标题，不引用题号。

**数值缺口的口径**：缺的是**数值**时，先在共享配置（`common/game_cfg.lua` 与 `common/cfg/` 的内容表）里放占位值并就地标「未查证」，同时在这里记一笔并写明影响哪条条款；不靠记忆、不写在工单或聊天里。真实数值到位后只替换配置，不改玩法判定（见 [ADR-0029](adr/0029-scope-completeness-and-placeholder-first.md) 第三节）。

### 近战与范围组起手与走廊宽度

问：电鳗放电、帝王蟹乱刺、蟹老板双击与冲撞的起手各几秒？鳄雀鳝的「间隔 1.5 秒」是否可直接当作起手窗？冲撞线形预警走廊取多宽？

现状：正文只给节拍与伤害。逐招表 [未查证] 占位：电鳗放电 0.5 秒；帝王蟹乱刺起手 0.5 秒（六刺仍按 0.2 秒间隔）；蟹老板双击 0.5 秒、冲撞 0.5 秒且走廊宽 2.5 米；鳄雀鳝以 1.5 秒攻击间隔兼作起手窗（表未单列起手）。虾霸的起手取 2 秒攻击节拍，蟹老板旋转取首段碰触前的 1 秒。以上都落在 `common/cfg/boss_moves.lua` 的 Warning.WindupSec / Width，真实数值到位只替换该表；12-49～12-51 的试玩可读性仍待整批取证。
## 逐题

### 他人抢救的耗时与打断规则

问：他人抢救濒死玩家要按几秒结算？抢救过程中施救者被攻击是否打断、被打断后进度是否清零？

现状：规格只写「2 米内可抢救」「成功后恢复血量上限 10%」，耗时与打断都没有。`common/game_cfg.lua` 的 `GameCfg.Rescue` 里 `DurationSec = 2`（耗时）、`InterruptMoveMeters = 1`（施救者移动打断阈值）、`InterruptOnDamage = true`（施救者受击打断）三项均就地标 `[未查证]`；2 米范围与 10% 恢复是规格原文，不在此列。

待定：由策划补一条数值与打断规则；补上后只替换上述三个配置字段，不改 `server/world_host/player_life.lua` 的相位推进与 `server/world_host/life_facade.lua` 的抢救复验，也不改 `tests/native/spec/09_rescue_test.lua` 的幂等断言。占位期间代码仅保证「两米内发起、耗时到点结算、打断回濒死、重复只算一次」这条路径完整，不宣称数值已获策划确认。

### 队伍界面的布局

问：队友头像与血量显示在屏幕哪一侧、最多显示几名队友、与自身血量条的距离是多少？

现状：规格只要求「在 HUD 上显示本队队友及每名队友的当前血量」并且「实机分辨率下可读、不与左上角自身血量重叠」，没给布局参数。

待定：由策划给一版布局草图；在补上之前按「右侧竖排、最多 2 名队友（小队上限 3 人）」实现，并在试玩取证时连同 9-23 一并复核。

### 邀请已在队伍中的玩家

问：A 队里的甲邀请已在 B 队的乙，应该拒绝这次邀请，还是让乙接受后自动从 B 队换到 A 队？

现状：规格只写「一支小队最多 3 名玩家」「只有在 2 米内才能邀请」，没有换队语义；换队还牵出「B 队少一人是否解散」的连带判定。

待定：由策划确认换队是否合法。在此之前实现按「拒绝邀请」处理（原因码 `target-in-party`），玩家要换队须先主动离队，
不替玩家隐式解散或离开原队伍。

### 金币页的占位汇率

问：真实商品 ID 与金币兑换汇率交付前，金币页用哪个占位汇率演示购买与到账？

现状：真实汇率与真实商品 ID 属于平台侧交付（原 7-25 的旧口径是「仓库内不自定取值」）。按 ADR-0029 的
占位优先口径，现在在共享配置 `GameCfg.Platform.Placeholder.CoinPage` 里放了明确标「未查证」的占位值：
`CoinPerUnit = 100`（1 元 → 100 金币），两份演示商品 6 元 → 600 金币、30 元 → 3000 金币，商品 ID 用
`placeholder.goods.coin.*` 前缀与真实 ID 区分。占位通道只在地图内到账金币，不发放真实付费权益（#261）。

待定：由策划与商业化确认正式汇率与商品 ID；到位后只替换 `GameCfg.Platform.Placeholder` 这张表并置
`Enabled = false`，玩法判定与结算顺序不动。

待定：由策划给一版逐招起手时长；补上之前不改判定，只替换表里带 [未查证] 的字段。

待定：由策划确认赠送走哪条路（丢地拾取还是单独请求，含在线/距离/跨区限制）；定案后补协议、补 `tests/native/spec/` 断言，再把 2-11 转 `evidenced`。

### 濒死界面的满血复活入口

问：满血复活（广告或 5 金豆）在濒死相位就要能直接结算，还是只作为死亡界面的入口？术语表把「解除濒死」记作抢救（Rescue），并把 Revive 限定为「死亡后重新回到场上」，而 11-19、11-20 要求「濒死与死亡界面都提供满血复活入口」。

现状：本单只把广告入口开到濒死相位（11-19），金豆入口仍只在死亡相位（11-20 保持 unverified）。濒死相位结算没有另造路径：仍由 `server/world_host/player_life.lua` 的 `full_revive` 这一个单点完成（满血、饥饿至少 10%、不带虚弱），濒死倒计时与在飞抢救一并撤掉，成功与免费倒计时仍互斥。

待定：由策划确认术语与入口口径。若金豆入口也要开到濒死，只需去掉 `PlatformRevive` 里「金豆只走死亡相位」的那一行守卫，复活动作与断言不动；若要收回广告入口，同样只改那处相位守卫与客户端按钮可见性。濒死界面两枚按钮的布局可读性属试玩口径（11-40、11-41），本单未试玩取证。

### 濒死相位广告播放期间暂停的倒计时

问：11-28 写「广告或支付进行期间，免费复活倒计时暂停」，但濒死相位里跑的是 15 秒濒死倒计时而不是免费复活倒计时；广告播放期间该不该一并暂停濒死倒计时？

现状：实现按同一意图暂停濒死倒计时——不暂停的话，玩家在看广告的途中会被判死亡，11-30 的「只复活一次」也随之失去意义。取消 / 失败 / 超时后起点平移暂停时长（`server/world_host/player_life.lua` 的 `resume_platform`），既不重置成满格也不提前到期。断言在 `tests/native/spec/11_ad_revive_placeholder_test.lua` 的 11-28、11-29 两例。

待定：由策划确认暂停范围。数值不受影响，只关相位推进的时机。

### 激励广告的真实交付参数

问：真实广告位 ID、广告播放时长与 failEvent 是否触发，取什么值？

现状：真实广告位由商业化后台交付，仓库里只有占位标识 `placeholder.ad.revive`（`GameCfg.Platform.Placeholder.Ads.revive`）与商品名 `GameCfg.Platform.Ads.revive`；等待上限 `GameCfg.Platform.FlowTimeoutSec = 60` 是 [未查证] 占位值（官方无取消 / 失败事件时的唯一兜底）。占位通道能走通成功 / 取消 / 失败 / 超时四条结局，但不拉起真实广告、不发放任何平台权益。

待定：由商业化后台交付广告位与时长；到位后只替换 `GameCfg.Platform.Ads.revive` 的 goodsId / adTag 与 `Placeholder.Enabled`，判定与断言不动。真实广告结论只在真实平台上取，本行的占位通过不算渠道结项。
