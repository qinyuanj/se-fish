# 0020 测试耗时以默认环境下的同轮中位数为准

**Status**: accepted

[耗时基线](../test-timing-baseline.md) 测得 `test fast` **11.14 s**、`test full` **34.5 s**。这批数字曾被当成「干净环境」读数，即编辑器客户端没开时的值，于是「`fast ≤ 5 s`」这类判据看起来必须绑一个特殊环境才能验收。

这个前提不成立。**默认环境就是编辑器开着**——agent 与人都在同一台机器、同一个编辑器里干活，把「先关编辑器」写进验收流程，等于往判据里塞一条没人会执行的纪律。实测也不支持这个前提：本机 12 核，编辑器两个 `client` 进程 5 秒吃掉 12.06 CPU 秒（≈2.4 核）的情况下，`test fast` 连跑三次是 **10.141 / 10.937 / 9.953 s**，离散约 10%，读数完全可用。基线报告里那个约 1.9 倍的掉速，测的是编辑器**正在跑地图**、物理与渲染把 CPU 抢满的瞬间，不是「进程开着」。

所以把可信度判据从「环境干净不干净」换成「这次读数稳不稳」。

## 决定

1. **不检测环境，不打印环境标签**：`tools/test.lua` 不看 `client` 进程，跑完只留 busted 的统计行。
2. **默认环境即验收环境**：目标值 `fast ≤ 5 s`、`full ≤ 60 s` 适用于日常状态，不附加「先关编辑器」这类前提。
3. **基线取同轮连跑三次的中位数**：单次读数不作为基线；三次之间离散超过约 20% 时本次读数不参与比较，重跑一轮。
4. **不做两套判据**：不设「编辑器忙时放宽到 ≤10 s」这类口径——两套判据在实际执行中会退化成「挑一套好看的报」。
5. **并行的前提是先有默认环境下的基线**，不要求先关编辑器。

## 理由

判据的用途是回归比较：同一份代码今天 10 s、明天 20 s，得能判断是退化还是噪声。离散度直接可测，环境不可测——同样「编辑器开着」，挂两个空闲进程与正在跑地图对 CPU 的影响差一个数量级，靠进程名分辨不出来。测能测的东西。

## 后果

- 判据在谁的机器上都直接可执行，不需要事先确认什么。
- 每次 `test` 少起一个 `tasklist` 进程。
- 单次读数只能回答「有没有坏」；要当基线得同轮连跑三次看离散。目标值 `fast ≤ 5 s`、`full ≤ 60 s` 目前只在 [#205](https://github.com/qinyuanj/se-fish/issues/205) 跟踪，**尚未进[开发工作流](../agents/workflow.md) 的完成判据表**——`fast` 还没达标（写下时 10.0 s；2026-11-18 删低价值测试 + 两两覆盖提速后复测为 7.95 s，见[耗时基线](../test-timing-baseline.md)的复测段），现在写进判据表只会让每一次改动都卡在同一条上。

## 备选方案（拒绝）

1. **检测 `client` 进程的 CPU 增量再判忙不忙**：比数进程强，但仍要猜「多少算忙」——探测、阈值、以及在没这进程的机器上的分支，为一条可以绕开的判据付出结构成本。
2. **要求人手工记录环境**：本仓已有「先列失败方式」「试玩优先」这类靠纪律维持的约定，再加一条只增加遗忘概率。
3. **检测到编辑器就自动跳过**：跳过把「有没有坏」这个信号一起丢掉。
