# 0013 区域几何以场景区域标记为准

**Status**: accepted

美术重做七区场景后，区域几何不再整体平移：各区相对位移不同、虾池单独重做、礁石岛只剩假山石群，旧灰盒与 `GameCfg` 手写坐标同时失真。继续在 `GameCfg.Zones[*].Scene` 与 `GameCfg.Water.Zones` 里维护坐标，需要每次美术改动都人工同步，而且派生量（`AirCombat`、`BossArena`、`Flight.FallbackBounds`、航线目的地）各自引用一份，改一处漏一片。

决定：区域几何的唯一事实源是场景里的**区域标记**（每区边界盒、可钓水域盒与水面高度、安全落点、去/返程摆渡点、烧烤点、抽奖点、鱼饵刷新点），运行时按名读取；`GameCfg` 只保留数值与内容配置，不再存区域坐标。标记沿用既有命名（`Z3_Water` 等），保留现有按名解析代码的入口。旧灰盒几何删除，不再作为任何判定依据。爆炸半径等票面数值（火箭筒 5 米、烤糊 3 米）不属于区域几何，不受影响。

2026-11-04 场景回退后的重做补充了标记合同：边界由四面空气墙的位置与尺寸解析，点位由具名标记解析；不规则水岸用不重叠的轴对齐水域标记覆盖，不拿整片 `深水` 或美术装饰的包围盒代替可钓水域。玩法只依赖稳定的 `Z*` 名称，摆渡车、烤架等美术件不是运行时查找入口。每轮试玩启动时统一解析并校验，缺标记、重名或尺寸非法明确失败；该轮内使用快照，编辑后的坐标在下轮试玩生效。标记先建齐，消费方迁移完成后再删旧几何与配置，避免中间版本仍读旧坐标。

06 礁石岛在地形补齐前保留临时可行走地面，不用假山石包围盒冒充正式岛面。空场景文件夹可以清理，但以回读无子项且没有运行时按名引用为前提；不能归组的地形不因此强搬或删除。

备选方案（拒绝）：把实测坐标写回 `GameCfg` 一次性止血——本轮即可恢复，但下一次美术改动会重演同样故障；保留灰盒作为隐藏载体——省一轮重建，但灰盒与新地形重叠处仍有双重碰撞与穿帮风险。

后果：美术摆标记成为区域交付的一部分，缺标记的区无法验收；`GameCfg` 末尾的折返变换退役；旧虾池七区统一模板口径随之作废。摆渡目的地也必须从标记读取，不能只迁移上船点。决定记录见 [#65 美术重做后的区域重对齐](https://github.com/qinyuanj/se-fish/issues/65)。

## 2026-11-28 修订：编辑态导出只读几何表、可钓水域方案 A 与交互提示定案（#403 / #408）

随着场景动态单位治理（[#403](https://github.com/qinyuanj/se-fish/issues/403)）推进，全图 804 个预摆 `WorldUnit`（含 189 个 `Z*_Water*`、28 面空气墙、48 个纯点位标记）与 14 个零监听空壳 `TriggerUnit` 在进游戏时全量加载为动态 Unit，而开启 `IsStaticOptimization = true` 后静态物体在运行期不再创建完整 Unit（`World:FindFirstChild` / `GetDescendants` 均不可见）。在 `editor-cli 0.20.17` / 编辑器 `1.0.38`（SDK `9.0.315`）真实试玩环境下完成两道前置可行性实机探针（[#408](https://github.com/qinyuanj/se-fish/issues/408)），据此修订本决策：

### 一、唯一编辑真源升级为「编辑态校验 → 只读几何导出表」

- 场景内具名标记仍是唯一编辑真源（美术/策划在编辑器内直接拖拽调整），但读取时机从「开服运行时遍历场景树」升级为「编辑态脚本校验并导出只读 Lua 几何快照表（仓库纳入版本管理，运行期直接读取）」。
- 01 鱼塘与 02 虾池 6 处历史命名统一收口为 `Z1_Shop`、`Z1_Fisherman`、`Z2_Shop`、`Z2_Fisherman`、`Z1_FerryOut`、`Z2_FerryReturn`。
- 缺标记、重名、越出本区边界、边界墙朝向/尺寸非法、水域重叠在导出期直接报错阻断；`ZoneMarkers` 运行期优先加载只读导出表（同时保留对测试夹具 world 的解析能力），不再依赖运行时场景树中的动态标记单位。
- 由此，28 面边界空气墙与 48 个纯坐标点位标记（安全落点、摆渡点、抽奖点、烧烤点、17 个鱼饵刷新点）均可全量开启 `IsStaticOptimization = true`（纯点位同步关闭渲染/碰撞/触发/物理），运行态动态标记单位清零。

### 二、探针 ① 实测与可钓水域选型：定案回落方案 A（导出只读水区表 + 标记静态不可见化）

在完成 7 区原生 `WaterUnit("深水")` 去重叠与高度对齐（`topY = -0.250 == SurfaceY`，7 块互不重叠）及 06 礁石岛 11 块临时地块静态化后，实测方案 B（原生 `WaterUnit` + `PhysicsService:Raycast` 判水）四条硬门槛：

1. **硬门槛 1（空间查询区分水面与陆地）— 未通过**：开启静态优化的装饰与临时地块在射线命中时 `RaycastResult.Instance == nil`，且无法被 `RaycastParams(Include/Exclude)` 过滤；高空射线（`y=50 -> -10`）被水面上方树冠、岩石、栈道与石拱截胡，产生 **13 处漏判**；低空射线（`y=1.5 -> -2.5`）起点落入厚地块（如 06 `Z6_Land` 顶面 `y=6.0`）内部后会穿透陆地直接命中下方 `WaterUnit`，造成陆地误判入水；且 06 内池 `Z6_PondFloor` 顶面 `y=0.00` 高于水面 `-0.25` 导致内池无法被射线命中。
2. **硬门槛 2（300 次高频判水耗时）— 通过**：实测 3000 次纯数学判水耗时 `2 ms`（折合 300 次约 `0.20 ms`），3000 次 `PhysicsService:Raycast` 耗时 `1 ms`（折合 300 次约 `0.10 ms`），性能同量级。
3. **硬门槛 3（`towardWater` 与 07 首领 `cruise_water`）— 未通过**：16 向放射射线在 Z6 因内池被 `Z6_PondFloor` 遮挡，算出方向与真值点积为 `-0.92`（反向逃离内池）。
4. **硬门槛 4（全 7 区零误判）— 未通过**：189 个水域中心点混淆矩阵 `HI_RAY_50` 为 `TP=176, FN=13`，`LO_RAY_1.5` 为 `TP=182, FN=7`，`SURF_RAY_0.2` 为 `TP=188, FN=1`（且低射线存在陆地穿透误判风险）。

按「4 条硬门槛任一不达标即回落方案 A」规则，正式定案 **方案 A**：
- 保留纯数学判水算法（`MathWaterJudge`）、精确 `towardWater` 与 07 首领 `cruise_water`；
- 将 189 个 `Z*_Water*` 纳入编辑态只读几何导出表；
- 场景中 189 个 `Z*_Water*` 关闭渲染/碰撞/触发/物理并开启 `IsStaticOptimization = true`，运行态动态水域标记清零；
- 7 块整理对齐后的原生 `WaterUnit("深水")` 负责视觉水面、游泳浮力与入水表现（`topY = -0.250 == SurfaceY`）。

### 三、探针 ② 实测与交互提示选型：定案回落自研气泡 + 导出坐标

在真实试玩服务端与客户端对原生 `ProximityPrompt` 做 4 项实测：

1. **服务与输入管线**：`game:GetService("ProximityPromptService")` 在服务端与客户端均返回 `nil`；`ProximityPrompt:InputHoldBegin()` / `InputHoldEnd()` 为 `nil`（方法缺失）。
2. **键鼠与触屏触发**：无论是服务端/客户端运行期创建的 `ProximityPrompt`，还是编辑态预摆挂载的 `ProximityPrompt`，玩家靠近至 1~2 m、切换 `Enabled` 并按下 `E` 键（`vk=69`）后，`PromptShown`、`PromptHidden`、`Triggered` 全部零触发，画面亦无原生提示界面渲染，无法满足键鼠与手机触屏双端可用门槛。
3. **多提示互斥与 `BodyScale` 动态半径**：虽然客户端可本地写入 `MaxActivationDistance` 属性，但因底层显示与触发服务尚未启用，互斥与触屏交互均不可验证达标。
4. **静态优化单位挂载**：编辑态挂在 `IsStaticOptimization = true` 单位下的 `ProximityPrompt`，进游戏后父级被静态优化剥离，`ProximityPrompt` 退化脱锚挂至 `World` 根节点。

按「触屏或动态半径不达标即自动回落」规则，正式定案 **自研气泡 + 导出坐标**：
- 彻底退役 14 个零触发监听的空壳 `TriggerUnit`（商店 7 + 渔民 7）；
- 服务端与客户端全部 38 个交互点（7 商店 + 7 渔民 + 7 抽奖 + 5 烧烤 + 12 摆渡）统一从只读导出几何表读取锚点坐标，不再运行时查找 `TriggerUnit` 或坐标标记；
- 维持并完善现有客户端响应式 `EUISceneNode` 交互气泡、单选互斥展示、键鼠/触屏统一点击以及随玩家 `BodyScale` 同步放大的动态交互半径；
- 19 个无 NPC 设施无需保留任何运行期动态锚点，将标记/装饰/地块类动态 `WorldUnit` 压降至 0；全图仅保留 7 个明确豁免的钓鱼佬站桩外观作为轻量非静态 `WorldUnit` 以支持客户端按区脉冲缩放反馈（见 #407）。
