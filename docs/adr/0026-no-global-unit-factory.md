# 0026 运行期单位不建全局工厂，只定四条规则

**Status**: accepted

**Unit / 单位**：引擎对象树中的对象本体，可由编辑器预置或 `CreateUnit` 创建。Unit 不等于游戏实体：一个游戏实体可含多个单位，界面节点也是单位。运行期建点清单见 #206 台账。
  _Avoid_: 对象、实体、game object、object（指单位时）

脚本运行期经 `CreateUnit` 建出的单位原有 **73 个建点**，各自为政：十个建点不给单位命名，同一个「建完记住、用完销毁」的动作在九个界面里写了五种互不相通的记法，另有五处根本不销毁。想回答「这条鱼获、这个投掷物是谁建的、谁负责拆」，只能整仓搜索。

最直觉的答案是「建一个全局单位工厂，所有建点都走它」。本 ADR 记录为什么**不**这么做，以及改用什么。

## 决定

1. **不建全局单位工厂**：`CreateUnit` 保持现址调用，不在入口上加统一包装。
2. **不建统一挂载容器**：存量单位继续挂世界根，换父级的风险大于收益。
3. **用归属登记解决「谁负责拆」**：[`common/OwnedUnits.lua`](../../common/OwnedUnits.lua)（#207）给 `Track(owner, unit)` / `Clear(owner)` / `Count(owner)` 三个函数，纯 Lua、无引擎依赖、两端共用；所有者可以是任意表或字符串标识。
4. **四条规则，只约束新代码与正在改的代码**，不做全量改名：
   - **归属**：建完必须登记到所属所有者的登记表；销毁走 `OwnedUnits.Clear`，不依赖父子级联。
   - **命名**：单位名 = 模块前缀 + 业务标识；禁止裸固定名；没有实例标识的至少带所有者标识（`<用途>_<UnitId>`）。同一个父节点下同时存在的同类单位必须按名可区分。
   - **回收**：每个建点必须在 #206 台账写明回收路径（定时自回收 / 显式销毁 / 池化 / 父子级联）；写不出来的算缺陷。
   - **事件桥**：不新增第四套「先查后建事件单位」；官方包内现有的三套（`common/packages/modifier_system/event_defs.lua`、`common/packages/ability_system/event_defs.lua`、`server/packages/ability_system/event_bridge.lua`）原样保留。

## 反直觉的结论：73 个建点里只有约 13 个能动

整理前 73 个建点 = 自研 61 + 官方包 12。这个总数很容易被读成「有 73 件事要做」。实际不是：

- **官方包 12 个只记录不改造**。它们随包升级被覆盖，改了等于没改，见 [ADR-0005](0005-packages-as-external.md) 与 [ADR-0010](0010-packages-as-business-code.md)。可覆盖的上限只有 61 个。
- **自研 61 个里，有 5 个是零调用死代码**（原序 3、4、47、48、49：通用头顶血条、`Util:WeldTo`、`Util:MarkPointPart`、`FXUtil:PlayFX`），直接删掉，剩 **56 个在用**。
- **这 56 个里，真正需要动的只有 13 处**：
  - 删死代码 **5 处**（即上面 5 个）；
  - 补缺失销毁 **5 处**（原序 13、14、15、16、18：抽奖与商店的气泡按钮文字、摆渡倒计时）；
  - 命名带实例标识 **3 处**（原序 53 投掷飞行物、59 鱼本体、70 与 71 近战武器挂点与命中盒——后两个同属一次挥击，按处计一处）。
- 自研在用的 56 个里，被改到的建点只有 **9 个**（补销毁 5 + 命名 4：投掷飞行物、鱼本体、武器挂点、命中盒），其余 **47 个本来就干净**：有名字、有回收路径，不动。9 个界面模块是另一条轴（记法统一到归属登记），不增删建点。

按「一次操作算一处」计，整轮整理实际改到 **13 处**（近战的武器挂点与命中盒同属一次挥击，算一处；按建点计是 14 个）与 **9 个界面模块**；剩下 **59 个建点**（官方包 12 + 自研本来干净 47）永久留在已知债里。换句话说，73 这个数字听起来像一份工作清单，实际只是一份现状清单。

## 理由

**工厂覆盖不了它想覆盖的东西。** 61 个可覆盖建点里，界面占 40 余处，而这九个界面已经各有私有 `create` 封装（`ScreenMain.button`、`ScreenShop.track`、`ScreenGM.create`、`ScreenCompendium.Screen:Create`、`ScreenBlindbox.Screen:Create`、`ScreenLottery.createNode`、`ScreenGrill.create`、`ScreenPlatform.Panel:Create`、`ScreenSurvival.create`）。工厂进来，只会成为第十套封装。

**参数差异大到工厂只能做属性表透传。** 界面建的是属性表（`kind` / `parent` / `name` / `x` / `y` / `w` / `h` / `props`），挂点建的是骨骼参数（`SocketName` / `SocketOffset` / `SocketRotation`），触发器建的是几何（`PhysicsMeshId` / `Scale` / `Position` / `Rotation`），事件建的是名字。把这些收进一个函数，接口只能是 `factory(kind, values)`——那就是把 `CreateUnit` 改个名，是假统一。

**真正在流血的是「建了谁负责拆」，不是「从哪个函数建」。** 五个不销毁的建点、五种互不相通的记法，都与入口形状无关；它们由归属登记加一条台账回收栏解决。

## 拒绝的方案

1. **全局单位工厂**：见上，成为第十套封装、假统一、且没有解决真正的欠账。
2. **统一挂载容器**：引擎对世界直接子节点的同步与物理行为没有验证过；存量单位（鱼获、掉落、投掷物、命中盒）挂世界根已通过试玩验收，换父级的风险大于收益。本决定只约束新代码，存量落根进已知债。
3. **全量改名到统一前缀**：改动面覆盖 56 个建点，收益只是名字好看，且会把官方包与自研代码的对照关系搅乱。四条规则只约束新代码与正在改的代码。

## 后果

- 新代码评审有四个可检查项：台账回收栏有没有填、名字带不带业务标识、建完有没有登记、有没有新增事件单位建法。
- 不新增抽象层：`CreateUnit` 的调用点数量与位置不变（删死代码后 68 个），改的只是名字与回收。
- 官方包 12 个建点永远在台账里；包升级后需按台账重新核对，不能指望它们自己变好。
- 已知债落成台账末尾一节：官方包 12 个建点、挂世界根的存量单位、近战行为的包内副本永不装载但随包一直在、用受击体单位类型冒充隐形受击体、同屏几十个同名兄弟节点。
- 本次落地的三处命名：`ThrowProjectile_<userId>_<投掷序号>`、`FishCarrier_<鱼实例序号>_<FishId>`、`ToolMount_<UnitId>_<挥击序号>` 与 `MeleeHitBox_<UnitId>_<挥击序号>`。
